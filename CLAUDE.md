# CLAUDE.md

## Project Overview

**SIGA System** — a personal task manager ("Categories, due dates & your daily system") built as a vanilla JavaScript single-page app with Google Sign-In and Firestore sync. No build system, no npm, no `package.json` — just static files served directly.

## Tech Stack

- **Frontend**: Vanilla JS (ES6 modules), no framework, no bundler
- **Styling**: Vanilla CSS with custom properties for light/dark theming; Inter via Google Fonts
- **Auth/DB**: Firebase v10 from the gstatic CDN (Google Sign-In + Cloud Firestore)
- **Drag-and-drop**: Sortable.js v1.15.0 (jsDelivr CDN)
- **Deployment**: Netlify → https://alex-great-app.netlify.app/

## Local Development

No install step required. Just serve the directory:

```bash
python -m http.server 8000
# or
npx http-server
```

Then open `http://localhost:8000`. (`.vscode/launch.json` is configured for port 8080.)

**Firebase config setup**: Copy `firebase-config.example.js` to `firebase-config.js` and fill in your credentials. This file is gitignored — never commit it. `index.html` does a `HEAD` fetch for it on load and shows the `#configMissing` banner if absent.

## Architecture

### State Management
All state lives in `main.js` as module-level variables:
- `tasks[]` — the canonical task array
- `activeUserId`, `currentUser`, `accountMenuOpen` — auth state
- `statusFilter`, `categoryFilter`, `searchQuery`, `sortMode` — view state
- `editingTaskId`, `editingTaskText`, `openTaskMenuId` — UI state
- `tasksUnsubscribe`, `isRemoteUpdate`, `lastSyncAt`, `lastSyncError`, `listenerActive` — sync state
- `renderedTaskIds`, `lastAddedSubtaskId`, `lastAddedSubtaskTaskId` — animation bookkeeping

### Task Data Model
```javascript
{
  id: string,          // Date.now().toString()
  text: string,
  done: boolean,       // legacy mirror of status === "done"
  status: "todo" | "doing" | "done",
  category: string,    // "General" | "Home" | "Work" | "Personal"
  dueDate: string,     // YYYY-MM-DD, or ""
  isDaily: boolean,    // pinned to the Daily drawer
  recurring: boolean,  // auto-resets to "todo" once per day
  subtasks: [{ id, text, done, status }]
}
```

`isDaily` and `recurring` are independent: `isDaily` controls drawer pinning, `recurring` controls the daily auto-reset.

### Persistence
- **Guest users**: `localStorage` key `todo_tasks_guest`
- **Signed-in users**: Firestore doc `users/{uid}/taskLists/default` (whole task array + `updatedAt` server timestamp), written with `setDoc({ merge: true })`
- On first sign-in, guest data migrates to Firestore automatically, guarded by the `todo_migrated_{uid}` localStorage flag

### Render Pattern
Every state change calls `save()` → persists to storage → calls `render()`. Full DOM teardown and rebuild on each change (acceptable at task-list scale).

### Sync and the `isRemoteUpdate` guard
`startRemoteSync()` (`main.js:178`) subscribes to Firestore via `onSnapshot`. When a snapshot arrives it sets `isRemoteUpdate = true` around the `tasks` assignment and `render()`, then clears it. `save()` (`main.js:132`) checks this flag and skips the Firestore write when set — this is what prevents the write → snapshot → write echo loop. **If you add a code path that mutates `tasks` from remote data, wrap it the same way.**

### Recurring tasks and the daily reset
`checkDailyReset()` (`main.js:156`) resets every task with `recurring: true` back to `status: "todo"` (and resets its subtasks) once per calendar day, stamping `todo_last_reset_{uid|guest}` in localStorage so it fires at most once daily.

**Known gotcha:** it is called exactly once, at init (`main.js:1770`), *before* auth resolves. At that moment `activeUserId` is still `null`, so it operates on localStorage guest data and stamps the *guest* reset key — then the Firestore snapshot overwrites `tasks` wholesale. For signed-in users the recurring reset therefore may not apply to synced tasks. If you touch recurring behavior, this is the thing to fix: re-run the reset after the first snapshot lands.

### Search
`searchQuery` filters on task text **and** subtask text (`main.js:925`), stacking with the status and category filters. Matches are highlighted via `highlightMatch()` — see the XSS note below. The empty state adapts, offering "Clear search" when a query is active.

### Filtering & Sorting
`render()` works on a shallow copy of `tasks`. Sort modes: `manual`, `dueAsc`, `dueDesc`, `newest`, `oldest`, `alpha`, `dailyTop`. **Default is `newest`.** Only `manual` persists order back to the `tasks` array (via the Sortable `onEnd` handler, `main.js:1379`); all other modes are view-only.

The build command (`node scripts/generate-firebase-config.js`) generates `firebase-config.js` from these vars and exits non-zero if a required one is missing. Publish directory is `.`.

## Key Conventions

- **XSS — read this before touching task text rendering.** Most user text is set via `textContent`, but there is one deliberate exception: task titles go through `textDiv.innerHTML = highlightMatch(t.text, searchQuery)` (`main.js:1039`) so search matches can be wrapped in `<mark>`. This is safe **only because** `highlightMatch()` runs `escapeHtml()` on both the text and the query before building the HTML. Never pass unescaped user input into that path, and never remove the escape step.
  - `escapeHtml()` escapes `&`, `<`, `>` — **not quotes**. That is sufficient for element content (its only current use) but is *not* safe for attribute values. Don't reuse it in an attribute context.
- **`normalizeTasks()` is the single migration boundary.** All data entering the system — from localStorage *and* Firestore — passes through it. It maps legacy `done` booleans to `status` strings, coerces `recurring` to a boolean, and backfills missing subtask IDs. Put new schema migrations here.
- **`autoPromoteParentStatus()` only promotes.** A parent becomes `"doing"` if any subtask is `"doing"`; it never demotes, and it skips tasks already marked done. Call it after any subtask status mutation.
- **Undo pattern**: `deleteTask`, `toggleDaily`, and `clearDone` all route through `showUndoToast()`, whose undo closure splices items back at their original index. Only one toast exists at a time. Keep new destructive actions consistent with this.
- Drag-and-drop (Sortable.js) is only enabled in `manual` sort mode; `updateSortableState()` toggles the `disabled` option. Since the default sort is now `newest`, dragging is disabled until the user explicitly picks Manual.
- Theme is persisted in `localStorage` as `"theme"` (`"dark"` or `"light"`), applied as a `dark` class on `<body>`; first load falls back to `prefers-color-scheme`.
- Category colors are duplicated between pills and filter dots in `styles.css` — General `#4b5563`, Home `#f97316`, Work `#2563eb`, Personal `#10b981`. Update both places.
- Mobile: drawers support swipe-to-close (`addSwipeToClose`, right-swipe >60px), touch targets are sized up, and safe-area insets are handled for notched phones. `styles.css` honors `prefers-reduced-motion` — keep new animations inside that guard.
- **No automated tests.** Verify manually across: task CRUD, subtasks, search, recurring reset, filters, sorting, drag-and-drop, auth flow (sign in/out + guest migration), daily/working drawers, offline sync status, mobile layout, and dark mode.
